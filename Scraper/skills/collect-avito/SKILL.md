# Сбор вакансий T&L

Версия 1.7.37, 29.10.2026. Корень проекта содержит `Scraper/extract.js`.
Используйте готовый `scripts/run.py`; его исходники не нужно читать для обычного
запуска. Не создавайте заново capture/export/setup-скрипты в /tmp.

Единственный источник `instruction_version` нового плана — строка «Версия» этого
файла; runner требует ровно одно объявление и записывает его вместе с хешем skill.
Ранее сохранённые планы и паспорта неизменны; расхождения фиксируют отдельным audit.

При явном разрешении на офлайн публикацию остановленного partition используйте
`finalize --partial-prefix --partial-instruction '<точное разрешение>'`: экспорт содержит лишь проверенный непрерывный префикс,
а partial_selection.json сохраняет хеши полного плана, очереди и raw, принятые,
исключённые и все оставшиеся ID. Исходные план и очередь не меняются. Частичный
экспорт не означает завершение части или отсутствие остальных вакансий.

Для продолжения опубликованного partial создайте новый run командой
`partial-suffix --source-run-id <partial> --run-id <новый>`: он проверяет
паспорт, копирует только неразобранный суффикс с исходными rank и фильтрами,
закрепляет хеши source plan/queue/selection/manifest и общий журнал родителя.
Завершённые артефакты и ранее прочитанные raw не меняются и не перечитываются.
Capture принимает карточку только если фактический URL вкладки и URL raw
совпадают с путём и origin очереди; пустая или иная вкладка останавливает сбор.
Для уже замороженного partition этот browser_batch guard допускается только после
note-change с причиной `Audited URL identity guard`, регрессионным тестом и
обновлением skill; предыдущие plan и extractor остаются неизменными.
Если после прежнего разрешения общий ledger уже READY, новое ограниченное
указание на диагностику фиксируют через `diagnostic-authorization` с ID и точным
текстом: это добавляет событие без изменения бюджета и не запускает браузер.

## Актуальная инструкция перед новым сбором

Ведущий **до запуска браузерного агента** выполняет `git fetch origin main`, готовит собственный
checkout/ветку от полученного `origin/main` и заново читает этот SKILL.md из него.
Обновляется весь checkout, чтобы инструкция, runner и extractor соответствовали
одному commit; отдельный файл из GitHub поверх старого кода не копируйте.
Для нового checkout используйте механизм worktree среды; при обычном Git —
`git worktree add -b codex/<уникальная-ветка> <новый-путь> origin/main`.
Незакоммиченные файлы существующего checkout не перезаписывайте.
Ошибка fetch останавливает новый сбор с сообщением человеку; устаревшую копию
молча не используйте. Если origin не указывает на командный репозиторий
`https://github.com/tooscl/salary-navigator` (HTTPS или SSH), используйте его
настроенный upstream: выполните `git fetch upstream main` и создайте checkout
от `upstream/main` вместо `origin/main`. При отсутствии такого remote сообщите
ограничение.

Передайте обоим агентам путь одного подготовленного checkout и его SKILL.md.
Оба агента читают этот файл, а не установленную личную копию или инструкцию
из истории. Между этапами fetch/update не нужен. `freeze` уже сохраняет
`instruction_version`, `instruction_sha256` и `code_git_commit` в plan.json;
в итоговой сводке укажите использованные версию и commit.
При каждом новом обращении участника после остановки сначала проверьте наличие
`Scraper/runs/<run_id>/plan.json` и сохранённой очереди/raw. Слово «продолжить»
и существующий браузерный агент сами по себе не закрепляют версию:

- Если plan.json, очередь и raw ещё не созданы, это подготовка до freeze.
  Снова выполните fetch командного main, подготовьте checkout от полученного
  commit и перечитайте общий skill **до возобновления браузерных действий**.
  Передайте агентам новый путь и версию; старый приостановленный агент не должен
  продолжать старую инструкцию. Сохраните условия задания, разрешения участника,
  журнал ошибок и остаток бюджета; новая версия не даёт новых попыток.
- Если план/очередь/raw уже существуют (в том числе частичный freeze), это resume:
  сохраняйте исходный checkout и закреплённые хеши. Обновление инструкции/кода
  внутри такого пакета — отдельное исправление по note-change, а не автоматическая
  замена перед продолжением. Не удаляйте план ради получения свежей версии.

Fetch обновляет remote ref, но не файлы старого checkout. Перед делегированием
проверьте `git rev-parse HEAD` и полученный `<remote>/main`: для подготовки без
плана они должны совпадать. Сообщите участнику версию skill и короткий commit.
Внутри непрерывного запуска между этапами повторный fetch не требуется.

Если после CAPTCHA сохранён raw со state NEEDS_HUMAN для `checkpoint.next_id`,
после явной свежей инструкции и `resume-browser` выполните офлайн
`run.py preserve-stopped-observation --run-id <id> --authorization-id <тот же id>`.
Команда сохраняет исходные байты и происхождение в `observations/<id>/`, проверяет
checkpoint, очередь, прежний sandbox и разрешение; затем освобождает raw-слот для
повторного чтения того же ID. Исходный sandbox не удаляется. Другие случаи требуют
разбора; новая CAPTCHA снова останавливает сбор. Регистрируйте изменения runner,
теста и skill через note-change до capture; история и бюджет не сбрасываются.

Если после freeze карточка закрыта, остановитесь и рассмотрите локальный snapshot.
Только после отдельного решения человека по конкретному ID и `resume-browser` можно
выполнить офлайн `run.py mark-unavailable --run-id <id> --id <ID> --authorization-id <id>`.
Инструкция разрешения должна содержать ID. Команда проверяет URL очереди, raw,
сообщение «Объявление закрыто.» в snapshot и checkpoint, сохраняет запись и хеши
в `unavailable.json` и оставляет raw неизменным. Такую карточку не считают
прочитанной и не включают в CSV; manifest и validation показывают исключение.
Разрешение не распространяется на будущие закрытые ID. Режим удалённых кандидатов
не поддерживается; ошибки и бюджет сохраняются. Исправления runner, тест и skill
регистрируют через note-change до capture/finalize.

Если человек явно разрешил исключать все последующие явно закрытые вакансии этого
run, после `resume-browser` закрепите разрешение `run.py closed-policy --run-id <id>
--authorization-id <id>`. Текущий остановленный ID обработайте `mark-unavailable`
с тем же authorization-id. В последующих пакетах capture учитывает только точные
видимые сообщения «Объявление закрыто.» или «Объявление снято с публикации.» при
проверенном URL и ID; сохраняет raw, короткое доказательство, хеш snapshot и
разрешение. CAPTCHA, 429, несовпадение ID и любые другие страницы останавливают
сбор как прежде. Новое разрешение на каждый подтверждённый закрытый ID не нужно.
Если сохранённый ответ подтверждает предыдущий вопрос, но сам не повторяет его
полный охват, передайте в `closed-policy --authorization-question` точный текст
этого вопроса. Политика сохранит вопрос и неизменный ответ с прежним ID; журнал
разрешений и бюджет не меняются. Используйте только фактически заданный вопрос.

При отдельном разрешении человека на все последующие карточки со статусом
«Оно ещё на проверке.» после `resume-browser` закрепите `run.py review-policy
--run-id <id> --authorization-id <id>`, затем текущую карточку оформите через
`mark-unavailable` с этим ID разрешения. Команда учитывает только точный видимый
статус в snapshot с совпадающим URL и заголовком «Объявление не посмотреть»;
raw и provenance сохраняются, запись имеет статус unavailable_under_review.
Закреплённое ранее разрешение на явно закрытые карточки продолжает действовать.
Новые блокировки или другие страницы требуют обычной остановки.

Для сохранённой активной карточки с единственной строкой «Оклад105 000 ₽» или
диапазоном вида «Оклад2 360 - 2 950 ₽» без
двоеточия, после отдельного указания человека и resume-browser используйте офлайн
`run.py review-salary-line --run-id <id> --id <ID> --authorization-id <id>`.
Общий разбор сверяет ID/URL, оба блока и каждую сохранённую строку, не допускает
неизвестные строки или свёрнутые параметры; создаёт offline_reviews с хешем raw.
Исходный raw неизменен, «Оклад» восстанавливается из точного сохранённого текста
при capture/finalize. Это офлайн-проверка существующего наблюдения, не новый
экстрактор и не новое чтение; иные шаблоны требуют отдельного рассмотрения.
Регистрируйте runner, тест и skill через note-change.

Если человек поручил исправить этот случай и продолжать очередь, до или после ручного
review закрепите проверенное правило командой `run.py salary-review-policy
--run-id <id> --id <исходный ID> --authorization-id <id>`. Последующие совпадающие
случаи capture проверяет тем же строгим офлайн-разбором и сохраняет отдельный
review с хешем каждого raw. Неизвестная строка, несовпадение ID или неполный блок
по-прежнему останавливают сбор; новые наблюдения и изменения extractor не нужны.
Если ответ подтверждает вопрос об обработке карточки, проверке последующих
аналогичных случаев и продолжении, передавайте в resume-browser точный контекст,
вопрос и ответ, сохраняя ID карточки и разрешения; новый бюджет не создаётся
при записи политики.

Если человек отдельно разрешил отмечать конкретное и последующие объявления со
статусом «Оно заблокировано после проверки.» как недоступные, после resume-browser
закрепите `run.py blocked-listing-policy --run-id <id> --authorization-id <id>`
и текущий ID обработайте через mark-unavailable с тем же разрешением. Проверяются
точная фраза, UNKNOWN_PAGE, заголовок и URL; raw и хеши доказательств сохраняются.
Это статус отдельного объявления: CAPTCHA, 429 и ограничение доступа по-прежнему
останавливают сбор. Предыдущие политики сохраняются.

## Подключённый профиль Aside до браузерных действий

Прочитайте актуальные `/browse`, `aside guide` и `aside guide repl`. Если CLI уже
доступен, сначала выполните `aside host profiles --host local --json`.
Отключённый профиль по умолчанию не означает, что CLI не установлен/не авторизован.
Используйте `profileId` с `connected: true`, без изменения постоянных настроек.
Если он один, выбор автоматический; если их несколько, используйте ранее явно
выбранный профиль либо уточните нужный. Если подключённых нет, попросите открыть
нужный профиль Aside. Не предлагайте переустановку/login без подтверждённой
ошибки установки/авторизации. Ошибка чтения списка — сообщить её, не перебирать
профили вслепую и не менять host/account ради обхода ограничения сайта.

Сохраните выбор для всего пакета в локальном окружении: `TL_ASIDE_PROFILE=<ID>`;
`TL_ASIDE_HOST` по умолчанию `local`, `TL_ASIDE_ACCOUNT` необязателен при первом
вызове: runner определяет его через `aside account status` и закрепляет явно.
Ранее выбранный профиль — ID, явно названный участником/ведущим в этом задании
или сохранённый в TL_ASIDE_PROFILE/локальном закреплении этого пакета. При работе
с другим настроенным host/account читайте список с теми же `--host`/`--account`.
Для ручного REPL фильтров передайте эти значения флагами:
`aside --host <host> --profile <ID> repl` (и `--account <account>`, если выбран).
Переменные TL_ASIDE_* читает наш Python runner, сам Aside CLI их не интерпретирует.
Передавайте одинаковые значения окружения каждому вызову preflight/freeze/capture
и в задание браузерному агенту; не полагайтесь на export из прошлого shell-вызова.
Preflight и runner проверяют список профилей и явно передают выбранный профиль
в REPL; при единственном подключённом профиле TL_ASIDE_PROFILE можно не задавать.
Runner закрепляет host/account/profile в локальном diagnostics/aside-target.local.json
перед первым probe и использует их при capture/resume. При отключении
закреплённого профиля остановитесь; другой профиль вместо него не выбирается.
Фактическую готовность подтверждает REPL probe, не один флаг connected.
ID профиля, списки аккаунтов и локальные настройки в Git не публикуйте.

## Первый запуск и неполное окружение

Если участник скачал проект впервые, просит настройку с нуля или preflight
обнаружил отсутствующие зависимости, прочитайте [FIRST_RUN.md](references/FIRST_RUN.md)
и проведите его до пробного CSV через общий run.py. Пункт FIRST_RUN.md
«gstack: агент готовит сам до открытия карточек» обязателен при отсутствии
/browse: проверьте имеющуюся установку, получите официальный Git-репозиторий,
прочитайте его локальную инструкцию, выполните setup для приложения/ОС и
проверьте результат. Участнику передавайте только конкретные действия, которые
требуют его доступа/подтверждения; после ответа продолжайте подготовку.
Не завершайте работу одним
NEEDS_SETUP: помогите подготовить Python, gstack, Aside и авторизацию, создайте
локальные настройки через scripts/setup_workspace.py и повторите проверку.
Входы в аккаунты, разрешения ОС и импорт профиля Happ подтверждает участник;
после его ответа продолжайте с места остановки. Режим сети не угадывайте и не
спрашивайте повторно, если он уже известен. Для Happ сначала проверьте известный
локальный конфиг и указанный в нём файл, затем стандартный внешний
`~/.local/share/tl-avito/collector.local.json` (на Windows/XDG — каталог из
setup_workspace.state_directory). Если файл есть и проходит статическую проверку,
используйте его через одинаковый --config/TL_AVITO_CONFIG во всех checkout;
не просите повторно выгружать JSON или импортировать профиль только из-за новой папки.
Если проверенного полного файла нет или маршрутизация отсутствует, сразу сообщите
это участнику и используйте локальный путь из [VPN_HAPP.md](../../../VPN_HAPP.md):
`setup_workspace.py --inspect-happ-local`, затем при отсутствии правил
`--prepare-happ-local` с внешними --config/--state-dir. На macOS скрипт читает
только известные preferences Happ и ключ connectedConfigJson, сохраняет исходник
и готовит полный avito-tunnel.json для импорта. Подписка/серверный доступ и ручной
экспорт JSON из подписки не нужны. Кэш не доказывает текущий активный туннель:
перед импортом сверяют выбранное подключение и актуальность, импорт подтверждает
участник. Два экземпляра Happ не выбирайте по догадке: нужен явный
--happ-preferences. Если кэша нет, сообщите конкретно это, предложите подключить
нужный туннель и проверить ещё один раз. Не ищите секреты по всему диску.
Для неподдержанного окружения/недоступного кэша остаётся запасной --mode happ
(routing-профиль) или предоставленный полный --happ-tunnel-json; не объявляйте
routing-профиль эквивалентом полного подключения. При уже подтверждённой настройке
используйте сохранённый конфиг, не готовьте новый при каждом checkout.
Наличие файла означает сохранённые правила, не подтверждённую активацию туннеля;
импорт/выбор в Happ подтверждает участник, Aside probe проверяет доступ браузера.
Существующие
настройки не перезаписываются; работающий туннель ради проверки не меняется.
Навык читается по пути из Codex/Claude Code; нестандартный путь /browse задаётся
через --browse-skill или TL_BROWSE_SKILL. Windows и другие агенты требуют
фактического теста, а не обещания совместимости.

## Окружение проверяет ведущий до делегирования

До запуска Luna/Terra (Claude — capture/review) ведущий завершает подготовку
окружения в выбранном checkout. Не передавайте браузерному агенту задание
«начинай сбор, заодно выясни, установлено ли окружение».

1. Найдите сохранённый конфиг по правилам выше. Если это первый запуск и режима
   сети/конфига нет, уточните режим один раз: Happ, другой клиент или без VPN.
   Наличие Happ на машине не доказывает активный туннель. При уже известном Happ
   и отсутствии проверенного конфига используйте локальную проверку/подготовку
   полного подключения по FIRST_RUN.md/VPN_HAPP.md. При наличии файла не запрашивайте его повторно.
2. При необходимости подготовьте Python/gstack/Aside по FIRST_RUN.md; проверьте
   подключённый профиль. Ведущий запускает
   `python3 Scraper/skills/collect-avito/scripts/preflight.py --probe-aside --json`
   с выбранным --config/TL_AVITO_CONFIG и настройками профиля. Это probe без
   открытия Авито. При блокирующей ошибке сначала устраните её/дождитесь действия
   участника, затем повторите только нужную проверку; агентов сбора пока не запускайте.
3. Отсутствие routing-файла — статус настройки сети, не поломка Aside. В первом
   запуске закройте вопрос режима/сохранения конфига до делегирования; не делайте
   вывод о VPN по одному предупреждению. Неподтверждённый live-маршрут сам по себе
   не блокирует обычный сбор при исправном Aside и согласованном режиме сети.
4. Передайте браузерному агенту готовый checkout, путь конфига и выбранный профиль,
   версию/commit и краткий результат preflight. Все выбранные пути сохраняются
   в локальных настройках вне Git, профиль — в локальном закреплении run.
   После первого запуска используйте сохранённые файлы: достаточно текущего
   preflight/probe, без повторной установки, экспорта JSON и импорта Happ.

`freeze`/`capture` сохраняют встроенные проверки на момент своего выполнения:
состояние окружения могло измениться. Это автоматический код, не повод вызывать
Terra. После успешного preflight ведущего браузерный агент не повторяет отдельную
ручную подготовку/probe перед freeze; он читает обязательные инструкции /browse
и переходит к фильтрам. При resume проверка ведущего не обновляет закреплённый
код/план и не сбрасывает журнал ошибок.

## Модели и делегирование

Сначала определите приложение исполнителя и прочитайте [HOSTS.md](references/HOSTS.md):
там точки обнаружения, native-файлы агентов, карта путей и точные параметры.

| Исполнитель | Браузерный пакет | Проверка/исключения и PR |
|---|---|---|
| Codex | Luna `gpt-6-luna`, low | Terra `gpt-6.1-terra`, medium |
| Claude Code | `avito-capture`, `model: haiku` | `avito-review`, `model: sonnet` |

Ведущий запускает одного браузерного агента на весь согласованный сбор,
включая все технические пакеты capture. На успешном пути проверяющего подключают
**один раз после завершения всех пакетов**, сразу для finalize, проверки сводки
и публикации. Размер пакета capture не является границей модельной проверки.
Не запускайте/не продолжайте Terra (в Claude — avito-review) после каждой
карточки или каждого успешного пакета и не передавайте ему промежуточные raw.
Во время сбора проверяющего вызывайте только при зафиксированной ошибке,
требующей разбора; передавайте ошибку и минимум относящихся к ней артефактов.
После устранения ошибки сбор продолжает тот же браузерный агент; финальная
проверка всех пакетов всё равно выполняется один раз. Смена агента не сбрасывает
бюджет ошибок. NEEDS_HUMAN не разрешает вызовом проверяющего продолжить браузер.
Это правило определяет число этапов делегирования, а не внутренних API-вызовов
модели: финальная проверка и публикация могут требовать нескольких команд.
Это маршрут навыка, не автоматическое изменение модели текущего чата. Не используйте GPT ID в Claude и не подменяйте оба этапа
моделью ведущего молча. Если native-делегирование/модель недоступны, сообщите
конкретное ограничение и согласуйте замену, продолжая независимую настройку.
Агенты этапов не запускают себя повторно и не создают агента на каждую карточку.
JS/Python извлекают и проверяют структуру без вызова модели на каждую вакансию.

Передайте короткое задание: checkout и его SKILL.md, run_id, точные фильтры,
лимит, этап, конфиг и условия публикации. Проверяющему — пути к артефактам,
не всю историю. Оба этапа используют одну очередь и общий failures.json.
NEEDS_HUMAN сохраняет силу при смене модели; публикация до проверки запрещена.

В --agent-model/--review-model передавайте фактическую модель; для Claude при
недоступном полном ID разрешён alias с явной оговоркой в сводке. Эти поля
не переключают модель. Сохраните имена/ID созданных агентов и сведения о
реальном исполнении. Для разработки навыка новый сбор не требуется: Codex
использует Terra для review и Luna для проверки понятности на сохранённых
материалах; Claude Code — соответственно avito-review и avito-capture.

## Обычный запуск

1. Прочитайте актуальный gstack `/browse`, весь браузерный доступ через Aside.
   Используйте свои сессию, вкладки, run_id и checkout. Независимые чаты могут
   работать одновременно; внутри своей очереди переходы последовательны.
   Не трогайте чужие вкладки, процессы или очередь. До ручного REPL выберите
   подключённый профиль по разделу выше.
2. Если профессии не заданы и нет ранее подтверждённого охвата, предложите
   выбор: наши топ-20 / все профессии без фильтра / конкретные профессии.
   Не начинайте автоматически «по всем». При явном «по нашим топ-профессиям»
   используйте [рабочий список](references/top-professions.md), уточнять его
   заново не нужно. Это все 20 в одном фильтре, первые N уникальных вакансий
   общей выдачи без квот. «Все профессии без фильтра» означает весь каталог
   Авито, а не топ-20. Уточняйте только отсутствующие существенные условия:
   географию, фильтры, объём или «до конца выдачи».
   Рабочий метод выбора из vacancy-filters.md сохранён: после успешного выбора
   не открывайте фильтр снова для ревизии всех 20 name/value, не сверяйте
   профессии/сортировку на каждой странице и не вызывайте Terra для этого.
   Свёрнутая панель может содержать лишь часть выбранных контролов; это не
   основание считать остальные профессии снятыми, останавливать сбор или
   переписывать экстрактор. Зафиксируйте выбранный охват и URL один раз.
   Один браузерный агент собирает все пакеты; Terra подключается один раз в конце.

### Следующие страницы и объём

Пагинация общая для любого объёма, отдельной настройки «на 200» нет.
`freeze --limit 5000` идёт по наблюдённой ссылке «Следующая страница» до 5 000
уникальных ID. `freeze --all-pages` вместо --limit идёт по наблюдённым ссылкам
до остановки обхода. Это не обещание доступа ко всем объявлениям сайта: сервер может
ограничить выдачу. Ссылки страниц код не конструирует, фильтры не перенастраивает.
Каждая прочитанная страница сохраняется, дубли по ID исключаются с сохранением
первого появления. При прерывании freeze --resume продолжает те же аргументы
с сохранённой страницы. Страница без новых ID не завершает обход при активной
ссылке Next на непрочитанную страницу. Явно отключённая Next подтверждает конец
наблюдённой выдачи; отсутствующая ссылка и ссылка на уже прочитанную страницу —
ограничения обхода, не подтверждение полноты. Число страниц не ограничено кодом.
План сохраняет исходный запрос, фактическое
число и причину конца; обычный limit для capture становится размером очереди.

Если замороженный `--all-pages` остановился прежней версией на `no_new_ids`,
а последняя сохранённая страница содержит непрочитанный Next, после снятия
блокировок и завершения текущих частей создайте отдельное продолжение:

```sh
python3 Scraper/skills/collect-avito/scripts/run.py continuation --run-id <tail> --parent-run-id <parent>
```

Команда офлайн копирует страницы и происхождение, проверяет очередь и сохраняет
общий журнал ошибок. Затем выполните `freeze --resume --run-id <tail>` с точными
аргументами `url`, `all-pages`, `geography`, `profession`, `segments`,
`filter-evidence`, `profession-scope` из выведенного request и фактическим
`--agent-model`; `url` остаётся исходным URL, следующий переход берётся только
из сохранённого Next. Старые ID исключаются, их исходные rank сохраняются;
новый план и паспорт ссылаются на копии исходного плана и очереди с хешами.
Если новых ID нет, сохраняется `continuation-empty.json` с причиной остановки;
пустой датасет не публикуется. Продолжение использует исходный failure ledger;
его нельзя делить через partition. При большом продолжении capture выполняется
пакетами в одном run. Исторические планы и raw не переписываются.
Это ещё не прочитанные карточки: «собраны» говорите после capture/finalize.
CAPTCHA/429, ошибка браузера, неверный ID или смена категории/региона остаются
ошибками по общим правилам; их не называйте концом выдачи. Для специального
режима N подходящих удалённых исходный целевой N не подменяется числом кандидатов:
исчерпание страниц завершает очередь кандидатов без ошибки пагинации.
Проверка числа совпадений и допуск экспорта остаются правилами этого режима. Карточки читает capture пакетами по 30 (размер пакета, не лимит).

Если человек явно согласился собрать только уже сохранённые страницы после неполного
freeze, используйте `freeze --resume --accept-saved --human-instruction '<точная инструкция>'`
с **исходными аргументами**, включая первоначальный limit, и `--retry-reason`.
Команда офлайн проверяет цепочку наблюдённых Next и ID, сохраняет исходный запрос,
указание человека и фактическое число в плане; она не запрашивает новые страницы.
Это не подтверждение конца выдачи и не снимает NEEDS_HUMAN: действуют общий журнал
и бюджет. Ошибки проверяют до повторного действия; без явного указания человека
не уменьшайте объём. Изменения runner и skill регистрируйте через note-change.

Для режима «N подходящих удалённых» используйте `freeze --limit N --candidate-limit M`:
M — явная верхняя граница кандидатов из одной наблюдённой выдачи, не меньше N.
Фильтр «Удалённо» должен быть подтверждён в snapshot. Capture последовательно
в одной Aside-сессии последовательно читает кандидатов до первых N карточек с точным видимым параметром
«Формат работы: Удалённо»; продвижение само по себе не определяет соответствие.
Остальные карточки не читаются. Повторяйте capture при IN_PROGRESS; если лимит
исчерпан, остановитесь без частичного экспорта и без перехода на другую страницу.
Finalize сохраняет все прочитанные raw и `exports/selection.json` с критериями,
причинами исключений и порядком, экспортирует только N совпадений. Структурная
ошибка останавливает сбор; отсутствующий параметр не считается совпадением.
Зарегистрируйте изменения runner, этого skill и регрессионного теста через
`note-change` до finalize, если они не входят в закреплённый commit.

3. Выберите точку входа по [паспорту маршрутов](references/vacancy-entry-routes.md):
   точный URL участника либо проверенная городская страница `/<город>/vakansii`.
   Сокращённое `/vakansii` в описании — имя раздела, не корневой URL сайта.
   `https://www.avito.ru/vakansii` не использовать: в проверке он вернул 404.
   Города нет в паспорте — сначала найдите его через фильтр внутри вакансий;
   после подтверждения добавьте наблюдённый маршрут в паспорт и тот же PR.
   Запасной путь применяйте после неудачи фильтра. Для «Всех регионов» сразу
   используйте проверенный `/all/vakansii` (`all`, две `l`) или точный URL участника.
   Подтвердите «Во всех регионах» после применения остальных фильтров.
   `/regions` — справочник городов. Не заменяйте общий охват одним городом.
   Если основной вход недоступен технически, запасной путь версии 1.4 —
   региональная главная → видимая категория «Работа и подработка»/«Работа» →
   наблюдённая выдача вакансий. Это исключение описано в паспорте; оно не
   применяется при CAPTCHA/429 и не меняет географию или условия задания.
   После входа используйте [проверенный путь фильтров](references/vacancy-filters.md):
   точная страница пользователя `/<город>/vakansii` → checkbox профессии → наблюдённая
   городская ссылка с сохранённым `/vakansii/` и профессией → проверка.
   Внутри настройки фильтров не уходите на главную, avito.st или общую ссылку
   города из футера; запасной маршрут используется только для восстановления входа.
   В собственном checkout от свежего `origin/main` откройте и настройте выдачу
   по `/browse`. Считайте snapshot, подтвердите выбранные контролы и фактический
   URL. Не угадывайте URL и кодировку фильтров. Для неизвестных фильтров держите
   один интерактивный Aside REPL, не переоткрывайте главную ради каждого клика.
4. Запускайте из корня проекта (полные пути к команде допустимы):

   ```sh
   python3 Scraper/skills/collect-avito/scripts/run.py freeze \
     --run-id <новый_id> --url '<наблюдённая выдача>' --limit 30 \
     --geography 'Все регионы' --agent-model <модель_браузерного_агента> --filter-evidence '<что подтверждено в snapshot>'
   python3 Scraper/skills/collect-avito/scripts/run.py capture --run-id <новый_id>
   python3 Scraper/skills/collect-avito/scripts/run.py finalize --run-id <новый_id> --review-model <модель_проверяющего>
   ```

   Для уже выбранных в UI наших топ-20 добавьте к freeze `--profession-scope top20`;
   для явно выбранного сбора без фильтра — `--profession-scope all`. Это фиксация
   выполненного выбора, не команда применить фильтры. План/CSV сохраняют весь
   выбранный набор независимо от свёрнутой панели. Без этого флага сохраняется
   обычное чтение profession из отмеченных контролов params[144170] и проверка
   необязательного --profession. Названия карточек профессию фильтра не определяют.
   Для одной выбранной профессии не передавайте `--profession-scope all`: укажите
   `--profession 'Комплектовщик'` (или точное имя выбранной профессии), без
   `--profession-scope`. Проверка freeze отклоняет all при видимом checkbox.
   Если старый план с all уже заморожен и карточки прочитаны, не переписывайте
   план или raw: после проверки причины используйте `finalize --run-id <child>
   --profession-from-observed-controls --profession-correction-reason '<причина,
   включая ошибку filter_evidence>'`. Команда проверяет parent/child provenance,
   хеши и цепочку всех страниц, одинаковые отмеченные профессии и сохраняет
   correction JSON, ссылку в sources и запись в manifest. Пустой или различный
   набор контролов останавливает экспорт. До finalize зарегистрируйте исправления
   runner, теста и skill через note-change; новые страницы не нужны.
   Если ошибка проверки кода обнаружена после завершённого finalize, исходный
   экспорт и паспорт не переписывайте. Для partition с correction используйте
   `post-finalize-review --run-id <child> --reason '<что исправлено и почему>'`:
   команда повторно проверяет происхождение, raw, CSV, correction, общий dataset
   и запускает регрессии; создаёт отдельный неизменяемый audit с хешами до/после.
   Publish проверяет audit и текущее состояние. После изменения источников audit
   более не действует: повторная команда добавляет новую запись со ссылкой по
   хешу на предыдущую; завершённые артефакты остаются неизменными.
   Capture/finalize проверяют сохранённые файлы/метаданные локальным кодом,
   не перечитывают UI. Законченные старые наборы не переписываются.

   `freeze` и `capture` сами выполняют preflight --probe-aside. Первичную
   проверку ведущего до делегирования это не заменяет; браузерному агенту не
   нужно дополнительно запускать отдельный preflight перед ними. Отсутствующий локальный конфиг даёт
   предупреждение; ошибка Aside блокирует работу. Браузерный агент не ищет
   VPN-конфиги по диску и не запрашивает JSON повторно во время freeze/capture:
   обычную настройку routing-профиля выполняет ведущий по процедуре выше;
   полный JSON — только необязательный явно выбранный вариант.
   Строгий аудит — отдельное явное задание.
   `TL_AVITO_CONFIG` или одинаковый --config у setup/preflight и freeze/capture
   позволяют использовать уже настроенный файл; без отдельного измерения
   live_route_verified=false.

   Очередь замораживается до карточек, сохраняются уникальные ID, порядок и
   отметки продвижения. `capture` читает технический пакет в одной Aside-сессии
   без вызовов модели между карточками;
   --batch-size ограничивает один вызов capture, по умолчанию 30. Если в
   замороженной очереди остались несобранные ID, тот же браузерный агент повторяет
   `capture --run-id <id> --batch-size 30` до завершения согласованной очереди.
   Успешный пакет сохраняет checkpoint; это не повод запускать finalize, Terra,
   unit suite или publish. Не объявляйте весь сбор завершённым только по состоянию
   CAPTURED: сверьте сохранённые ID со всей очередью. Новые страницы и увеличение
   лимита не следуют автоматически из пакетности и требуют согласованного режима
   отбора. Проверки кода во время capture продолжают выполняться автоматически.
   Прерванный freeze восстанавливается с теми же аргументами и --resume.
   Повторный `capture` продолжает по raw и
   checkpoint, не загружает сохранённые ID. Если до чтения карточек обнаружена
   неверная выдача, `run.py reselect --run-id <id> --reason '<причина>'`
   сохраняет исходные план и очередь в superseded-freeze и позволяет повторить
   freeze с подтверждённым URL в том же run; журнал и бюджет ошибок сохраняются.
   При наличии raw или завершённого manifest команда запрещена. Изменения кода,
   теста и skill зарегистрируйте через note-change до finalize.
   Полные тексты карточек не выводятся
   в контекст на успешном пути, только сводка. Искусственных пауз нет.
5. После всех пакетов передайте проверяющему пути к артефактам и краткую сводку
   один раз. Он выполняет finalize, проверку и разрешённую заданием публикацию
   в одном финальном этапе; при локальном показе publish не выполняется.
   `finalize` проверяет весь набор, записывает отдельный CSV/JSON, паспорт,
   регистрирует источник и пересобирает общий CSV. Новые параметры автоматически
   становятся колонками. Нормализация сохраняет названия; если обнаружен синоним
   существующего поля, исправьте общую нормализацию с регрессионной проверкой.
   Основной файл команды — `Data/dataset/vacancies.csv`; отдельный самодостаточный
   CSV — `Data/avito_runs/<id>/exports/vacancies_flat.csv`.
   Подробный контракт полей нужен при изменении схемы или обогащении:
   [Data/dataset/README.md](../../../Data/dataset/README.md).
6. Для обычного пакета достаточно проверок `finalize`, `build_dataset --check`
   и сверки краткой сводки. Повторять весь unit suite на каждом неизменённом
   сборе не нужно. При изменении кода выполните относящиеся к нему регрессионные
   тесты. Скрипт не объявляет, что человек прочитал каждую карточку:
   review_method явно фиксирует проверку отрисованного шаблона.
7. Опубликуйте, если задание не ограничено локальным показом:

   ```sh
   python3 Scraper/skills/collect-avito/scripts/run.py publish --run-id <id> \
     --summary '<условия отбора и существенное ограничение>' \
     --title 'Данные: 30 вакансий · без фильтров · Все регионы'
   ```

   Команда проверяет хеши, --check, актуальность main и отсутствие посторонних staged-файлов; добавляет
   только файлы сбора, производные данные и явно зарегистрированные исправления;
   создаёт commit/push/PR с краткой статистикой. --prepare-only только готовит
   stage и текст для просмотра. Прикрепите созданный PR к чату.
   При рассинхронизации main сохраните обе записи реестра и пересоберите
   производные файлы; инструкция нужна только при конфликте:
   [references/edge-cases.md](references/edge-cases.md).
   Проверьте обязательные checks/reviews, head SHA и выполните обычный merge
   с --match-head-commit. Не обходите защиту. Затем проверьте свежий origin/main
   в чистом checkout через build_dataset.py --check. Только после этого
   сообщайте «в main». Полный набор unit-тестов повторно не нужен без новых изменений.

## Ошибки: до пяти повторов и явное продолжение

Один run_id, checkout и локальный failures.json передаются всем агентам.
Бюджет общий для этапов, URL и исполнителей: исходная попытка и **до пяти**
повторов после технических ошибок. Сначала запишите фактическую ошибку:

```sh
python3 Scraper/skills/collect-avito/scripts/run.py record-error --run-id <id> \
  --stage filters --action 'выбор города' --message '<точная ошибка>' \
  --url '<текущая страница>' --agent <фактический_агент>
```

freeze/capture/finalize/publish записывают свои ошибки автоматически — второй раз
их не регистрируйте. Ошибки ручных действий (API, quoting, загрузка, фильтры)
записывает агент. Журнал и failure-report.md остаются в локальном diagnostics.

Перед повтором нужна конкретная коррекция по фактам, без слепого цикла запросов:
`run.py check-stage --run-id <id> --stage filters --retry-reason '<коррекция>'`.
Флаг `--immediate` существует только у `record-error`, не у `check-stage`.
Перед использованием проверяйте `run.py <команда> --help`. Для выбора checkbox
по свежему ref и разбора наблюдённой ошибки см. [рецепт фильтров](references/vacancy-filters.md).
Эта команда резервирует один повтор; повторные проверки того же активного этапа
возвращают тот же допуск и не тратят дополнительные повторы. После действия
нужно либо `stage-ok --run-id <id> --stage filters --evidence '<snapshot>'`,
либо record-error при фактическом сбое. Другой этап не начинают до завершения
активного. Повторная проверка не разрешает повторно запустить штатную команду:
активный повтор может быть использован действием только один раз, параллельные
команды одного run_id блокируются. После подтверждённого прерывания процесса
запишите record-error того же этапа и начните следующий разрешённый повтор. У штатных команд причина передаётся как --retry-reason; повторно
вызывать отдельный check-stage перед той же командой не требуется.

Успех не восстанавливает общий бюджет пяти повторов. Если пятый повтор тоже
завершился ошибкой (шесть неудачных действий с учётом исходного), NEEDS_HUMAN
останавливает работу. CAPTCHA, 429, ограничение доступа и неверный ID требуют
немедленной остановки без этих пяти повторов; для ручного record-error добавьте
--immediate. Не меняйте профиль/IP ради обхода. Смена агента, вкладки или URL
не сбрасывает бюджет. Дублирование проверки не считается новым действием.

Кроме заранее разрешённого однократного IP-повтора через 30 минут (раздел ниже),
после **новой явной инструкции человека** продолжить чтение сайта используйте:

```sh
python3 Scraper/skills/collect-avito/scripts/run.py resume-browser --run-id <id> \
  --human-instruction '<новое разрешение человека>' \
  --authorization-id '<стабильный ID этого сообщения/разрешения>'
```

Сохраняются ошибки и события, открывается новая ограниченная попытка с пятью
повторами. Повторный вызов с тем же authorization-id не пополняет бюджет;
после следующей остановки старое разрешение использовать нельзя. Если инструкция
человека строже бюджета runner, соблюдайте её предел отдельно. Агент не
генерирует новые разрешения сам: новый ID допустим только для новой инструкции
человека. Эта команда не устраняет CAPTCHA/другую причину блокировки и не
разрешает обходить её. После разрешения выберите продолжение по сохранённому состоянию:
если freeze ещё не начинался и есть только failures.json — обычный freeze;
если freeze прервался до сохранения плана — freeze --resume с теми же условиями;
если план/очередь уже есть — capture. Сначала проверьте checkpoint/raw, если
они существуют; сохранённые карточки не перечитывайте. Для задачи «из открытой выдачи» сохраните её наблюдённый URL
и работайте в собственной вкладке; attach к существующей вкладке не нужен.

Если человек разрешил только работу с уже сохранёнными данными, остаётся
resume-offline из раздела ниже: он никогда не открывает браузерный этап.
Старые NEEDS_HUMAN-журналы не разблокируются только от обновления версии.
Проверяющий может разбирать локальные логи и исправлять код офлайн; браузерные
итерации выполняются лишь в разрешённых рамках и через того же исполнителя.

## IP-лимитер: один автоматический повтор через 30 минут

Пользователь заранее разрешил этот сценарий 28.10.2026: при странице
«Подозрительная активность с вашего IP» / «Доступ ограничен: проблема с IP»
немедленно прекратите запросы, сохраните checkpoint и журнал, затем один раз
автоматически возобновите работу **не раньше чем через 30 минут**. Это узкое
исключение из требования нового разрешения после NEEDS_HUMAN для такой IP-страницы.
HTTP 429 с явным сообщением о подозрительной активности IP относится к этому
сценарию. Отдельная CAPTCHA, 429 без сообщения об IP, ошибка ID и прочие ошибки под это
разрешение не подпадают. Профиль, IP, VPN и фильтры не меняйте.

1. В локальном diagnostics/ip-cooldown.json сохраните run_id, checkout,
   blocked_at, retry_not_before (UTC, blocked_at + 30 минут), URL/next_id,
   authorization_id=`ip-cooldown-v1:<run_id>`, retry_used=false. Это один
   автоматический повтор на run_id, общий для всех агентов. Уже использованный
   повтор не разрешается заново после успеха или смены чата. Сообщите участнику
   время запланированного продолжения и создайте реальное отложенное выполнение.
2. В Codex используйте heartbeat через automation_update на 30 минут в этом же
   чате. В задании закрепите сохранённые checkout/run_id/профиль/конфиг, путь
   ip-cooldown.json и условие времени; до retry_not_before сайт не открывать.
   Напоминание без исполнения не подходит. При первом запуске heartbeat
   проверьте время: при раннем срабатывании не открывайте сайт и не расходуйте
   повтор, оставьте/переназначьте выполнение на retry_not_before. При наступлении
   срока проверьте retry_used, затем отключите дальнейшие повторы heartbeat. Для другого
   приложения используйте доступный штатный планировщик исполнения. Если такого
   механизма нет/создание не удалось, прямо сообщите, что автоматический запуск
   не назначен, и попросите человека продолжить через 30 минут; не обещайте
   пробуждение и не держите молча блокирующий sleep на полчаса.
3. В назначенный момент сначала атомарно создайте каталог
   diagnostics/ip-retry.claim (mkdir без exist_ok, под общим diagnostics этого
   run_id). Если он уже существует, второй запуск ничего не делает. Только
   получивший этот допуск агент отмечает retry_used=true и продолжает; каталог
   не удаляется и защищает от двух одновременных пробуждений. Выполните resume-browser с указанным
   стабильным authorization-id и human-instruction «Заранее разрешённый пользователем
   один повтор IP-лимитера через 30 минут, правило skill 1.7.22». Это применение
   сохранённого разрешения, не новая инструкция человека и не новый бюджет для
   серии попыток. История failures.json остаётся. При сохранённом raw NEEDS_HUMAN
   для текущего ID используйте preserve-stopped-observation с тем же authorization-id
   по процедуре выше; успешные raw не трогайте.
4. Через gstack /browse и того же браузерного исполнителя выполните ровно одну
   повторную загрузку остановленной страницы: freeze --resume до готового плана
   либо capture с checkpoint после готовой очереди. Эти команды сами открывают
   страницу заново; отдельную предварительную перезагрузку не добавляйте.
   Если freeze ещё не запускался (остановка на ручном шаге фильтров), один раз
   откройте сохранённый URL в своей вкладке и продолжите тот же шаг. Успех —
   нормальная LISTING либо DETAIL нужного ID без IP-страницы/капчи; успешный
   ответ инструмента сам по себе ещё не подтверждает снятие ограничения.
   Продолжайте существующую очередь, не начинайте сбор заново с первой карточки.
5. Если после этой загрузки ограничение осталось либо повтор завершился другой
   ошибкой (включая ошибку resume/preflight), сохраните её и остановитесь с NEEDS_HUMAN.
   Если штатная команда уже записала техническую ошибку, не повторяйте её запись:
   добавьте отдельное решение об исчерпании разрешения через record-error
   --stage ip-cooldown --action "stop after the only cooldown retry"
   --message "Единственный IP-повтор не удался; исходная ошибка уже в failures.json"
   --immediate с тем же run-id. Это отдельное решение политики, которое переводит
   журнал в NEEDS_HUMAN, а не новый повтор. Зовите человека, не
   назначайте второй таймер и не расходуйте обычные технические повторы.
   При успехе продолжайте обычный сбор. Любая следующая IP-блокировка этого
   run_id требует человека, поскольку автоматический повтор уже использован.

Обновление skill само по себе не запускает таймеры для старых остановленных
чатов: отложенное выполнение назначает владелец конкретного сбора при обработке
IP-блокировки. Блокировки чужих сборов не снимайте.

## Что требует участия агента

- CAPTCHA/ограничение IP/429: сохранить checkpoint и остановить переходы.
  Для наблюдённого IP-лимитера действует исключение «один повтор через 30 минут»
  из раздела выше; для остальных случаев автоматического обхода нет. Ошибка ID или полностью непрочитанный шаблон: REVIEW_REQUIRED, raw неизменяем.
  Пустое отдельное описание/адрес сохраняется пропуском по правилу выше. Краткое дополнительное ожидание
  до 5 секунд допускается только при наблюдаемом переходном состоянии страницы.
- Новый шаблон: изучить локальную диагностику; исправить **общий** экстрактор или
  runner, добавить воспроизводимый тест, обновить этот skill/ссылку на команду.
  Если extractor изменился, старые raw сохраняются; новое наблюдение получает
  новый run_id. Временный обход не считается завершённым исправлением.
- Расположение: проверьте location_raw и read_status.location. Экстрактор читает
  маркеры адреса или видимый соседний блок «Расположение», исключая карту,
  скрытые подсказки и описание. Пустоту не подменяйте URL или текстом вакансии; оставьте пропуск без дополнительного обхода.
  При разборе первая строка расположения содержит адрес; последующие строки
  могут содержать станции метро и районы и не считаются населёнными пунктами.
- Новый город: `finalize` повторно использует подтверждённые city→region из
  реестра. Неизвестные места требуют проверенного JSON `ID: {city, region,
  evidence}` через --placements. Цитата evidence и city должны встречаться
  в видимом расположении. Не выводите географию из описания или URL slug.
  Для обычного сбора используйте city-anomaly-policy blank без запросов
  дополнительного подтверждения пропуска. Ручное исправление по заданию участника:
  если город отсутствует, передайте `city: ""`, `city_unknown_confirmed: true`, регион и
  точную цитату региона в evidence. Исключение по ID сохраняется в реестре;
  остальные пустые города допускаются только как явно отмеченные пропуски. Исправления runner и skill после capture
  допускаются при регистрации через note-change; исходные и новые хеши сохраняются.
- Новая автоматизация фиксируется **в том же PR**: код, тест и обновление skill.
  До finalize зарегистрируйте каждый нужный файл:

  ```sh
  python3 Scraper/skills/collect-avito/scripts/run.py note-change --run-id <id> \
    --file Scraper/extract.js --reason '<новый случай и исправление>' \
    --validation '<какой тест выполнен и результат>'
  ```

  Повторите для теста и skill. Паспорт сохранит automation_changes, генератор PR
  добавит короткие bullets с файлами, причиной и проверкой. Код без этой записи
  не публикуется вместе с данными. Отдельный PR для исправления без сбора тоже
  должен описывать новый случай, тест и обновлённый маршрут запуска.

  Документационные изменения регистрируются через note-change и проверяются по
  источнику; отдельный тест обязателен при изменении кода сборщика, а не только
  текста инструкции. Для исправления валидатора также регистрируйте его тест.

## Техническая отметка military: только словарь названия

Все вакансии сохраняются независимо от военной тематики. Не исключайте их из
очереди/CSV, не открывайте дополнительные страницы ради классификации и не
поручайте Luna/Terra интерпретировать описание. При finalize готовый код
utils/title_flags.py выставляет military, military_keywords и military_rule_version
только по названию; общий build_dataset.py тем же правилом размечает актуальные
заголовки уже зарегистрированных строк без изменения исходных выгрузок.

Словарь military_title_v1: целые слова БПЛА, ЛНР, ДНР, СВО, ВАИ, тыл;
начала слов донецк…, военн…, тылов… (Донецк/Донецкая, военный/военнослужащий,
тыловой/тыловая). Регистр не учитывается, совпадения сохраняются в отдельном поле.
«Контракт», «доброволец», «служба», «долги» сами по себе не включены. Не расширяйте
словарь во время обычного сбора. False означает отсутствие словарного совпадения,
а не доказанную гражданскую вакансию; Донецк может пометить и гражданское объявление.
Словарь — воспроизводимый сигнал для последующего исследования, не вывод модели.

## Пропуски не требуют повторного обхода

Отсутствующее/неразобранное отдельное поле сохраняйте пустым. Не запускайте
повторные переходы, специальный разбор Terra, новый сбор или добор замен из-за
пустого формата работы, города, описания или адреса. Наблюдённые значения и raw
сохраняются; read_status и city_anomaly отмечают пропуск. Текст поиска не
подменяет характеристику карточки. Сводки количества пропусков достаточно.
Это относится к частично доступным данным: правильный ID/заголовок и прочитанный
блок параметров остаются обязательными. CAPTCHA/блокировка, другой ID, полностью
непрочитанная карточка или повреждённая структура по-прежнему останавливают сбор.
Не объявляйте частичную запись полной; отсутствие параметра — не ошибка шаблона.

Отсутствующий отдельный параметр (например, «Формат работы») при полностью
прочитанном блоке не является ошибкой экстрактора и не требует повторного обхода.
Оставьте пропуск; условие поисковой выдачи не подменяет наблюдённую характеристику.
Первые N результатов сохраняются с пропусками; режим «N подтверждённых совпадений»
используйте только когда он явно задан. Отметка продвижения сама по себе не
подтверждает и не опровергает значение характеристики. Разбор двух запусков:
[parameter-absence-review.md](references/parameter-absence-review.md).

## Данные и ограничения

Одна строка на вакансию, все наблюдённые параметры в колонках, полное описание,
пустые значения неизвестны. profession — фильтр отбора, без фильтра пусто.
Город/регион — размещение на сайте. Период зарплаты не выводится из выплат.
Обогащение не запускается без соответствующего задания, по умолчанию not_run.
Правила обогащения и resume с нестандартными карточками — в
[references/edge-cases.md](references/edge-cases.md), читать только при необходимости.
Raw/CSV/JSON, очередь, план и паспорт публикуются; DOM и screenshots остаются
локально в diagnostics. Завершённые наборы не переписываются.

Покажите количество принятых/новых/повторных ID, размер общей таблицы, путь к
CSV и PR. capture_seconds — измеренное чтение и сохранение карточек, отдельно
от setup/review-export/publication. Источник общей длительности — checkpoint; локальный timing.json показывает только последний RPC. observed_at не заменяет замер длительности.
Не обещайте скорость и расход токенов без сопоставимого измерения.

## Аномалии географии без повторного сбора

`finalize --city-anomaly-policy blank` (по умолчанию) оставляет нераспознанный
город пустым. `--city-anomaly-policy search_filter` заполняет его подтверждённым
единственным городом из плана/фильтра; для «Все регионы» такой режим запрещён.
Всегда сохраняются `location_observed`, `city__source` (card/search_filter/missing),
`city__evidence` и `city_anomaly`. Источник search_filter не выдаётся за текст
карточки; исходные raw и описание не меняются. Метро и районы после строки
адреса не считаются городами. Исторические строки могут не иметь city__source.

Если человек после NEEDS_HUMAN явно разрешил завершить уже сохранённый пакет
без нового сбора, запишите его инструкцию через `run.py resume-offline --run-id
<id> --human-instruction '<точное разрешение>'`. Это разрешает только finalize
и publish, сохраняет старые ошибки и по-прежнему блокирует freeze/capture.
Новая ошибка отзывает разрешение. Без новой инструкции человека команду не
вызывать. Вмешательство фиксируется в локальном журнале; raw не перечитывать
с сайта, существующий план/дату наблюдения не переписывать.


## Вкладка при остановке

Если участник явно указал существующую вкладку, определите её targetId через
`listBrowserTabs()` в выбранном профиле, не выводя полный список в отчёт, и
передайте `--tab-id <targetId>` в freeze/capture. Runner подключает вкладку и
не вызывает для неё closeTab. При остановке runner сохраняет собственную REPL
и локальный `diagnostics/browser-session.local.json` с PID, ссылкой на sandbox,
targetId и URL без query/fragment; `browser-tab.json` хранит только эти данные.
При сбое процесса или браузера сохранность вкладки не гарантируется. По отдельной
инструкции человека завершить удержание можно созданием файла
`release_marker` из `diagnostics/browser-session.local.json`.
Проверяйте, что пользовательская вкладка пережила завершение REPL; не закрывайте
её. Созданная runner вкладка удерживается до завершения проверки результата в Python; после успешной проверки REPL штатно освобождается. Первую freeze-страницу подключённой пользовательской вкладки runner не перезагружает.


## Публикация частей одной замороженной очереди

После freeze полной обычной очереди и до чтения карточек выполните офлайн
`python3 Scraper/skills/collect-avito/scripts/run.py partition --run-id <parent>
--batch-size <N> --prefix <prefix>`. Команда создаёт child run_id `<prefix>_01`,
`<prefix>_02` и далее: очереди — последовательные непересекающиеся интервалы,
исходный listing_rank сохранён. В каждой части хранятся полный план, очередь и
страницы родителя с хешами; capture/finalize повторно проверяют происхождение.
Общий локальный журнал ошибок и блокировка принадлежат родителю: не удаляйте
его checkout/diagnostics до завершения всех частей. Лимит группы — одна
коррекция после первой ошибки, после второй NEEDS_HUMAN; блокировки немедленны.
Каждую часть собирайте и публикуйте по порядку с отдельным PR; после слияния
синхронизируйте main и общий dataset перед следующим finalize. Родительскую
очередь напрямую не собирайте после partition. При отсутствии страниц выдачи
ранее запрошенного числа итоговый union ограничен фактически замороженной очередью.

Проверка и продолжение дочернего run требуют исходные локальные parent diagnostics
и partition.json: в свежем clone опубликованные страницы, план и очередь позволяют
проверить происхождение диапазона, но не восстанавливают приватный журнал ошибок.
`build_dataset.py --check` проверяет общий экспорт и не заменяет проверку provenance.

При отклонённой первой странице до plan/queue/raw, когда записана ошибка freeze и
остаётся разрешённая коррекция, `archive-partial-listing --run-id <id> --reason
<причина>` сохраняет её локально с хешами и исходными аргументами; после этого
`freeze --resume` выполняет новое наблюдение и не стирает бюджет ошибок. Не
применяйте это к уже принятым страницам, плану или карточкам.

## Наблюдение участника о границе выдачи

28.10.2026 участник сообщил, что интерфейс выдачи ограничен 30 страницами.
Фиксируйте это как сообщение участника и сверяйте с сохранёнными страницами
конкретного сбора. Не задавайте программный потолок: граница доступной выдачи
не подтверждает общее число объявлений сайта или отсутствие серверного ограничения.

29.10.2026 участник уточнил критерий доступной выдачи: сохранённое наблюдение
текущей страницы 30 и отсутствия активного дальнейшего перехода при неизменных
фильтрах достаточно для экспертного вывода о её границе; disabled Next желателен,
но не обязателен. Сохраняйте доказательство UI и отдельный review, не меняя
исходный план или результат extractor. Один `next_url: null` не подтверждает
состояние UI. Счётчик сайта не равен числу доступных ID; этот вывод не доказывает
полноту всех объявлений сайта.

Политики закрытых и других недоступных карточек проверяют разрешение в общем
родительском журнале partition; в дочерние каталоги копии журнала не создаются.


## Постоянное разрешение на недоступные карточки

По постоянной инструкции участника штатный capture автоматически регистрирует
проектную политику для каждой части. Событие с версией политики и источником
project_skill сохраняется в общем журнале один раз без сброса бюджета;
разрешение текущего сбора отдельно фиксируется локально. Для проверки
офлайн доступна `standing-unavailable-policy --run-id <child>`.
Автоматически исключаются только сохранённые подтверждённые статусы «Объявление
закрыто.», «Объявление снято с публикации.», «Оно ещё на проверке.», «Оно
заблокировано после проверки.», «Объявление удалено.», «Объявление больше
недоступно.», «Объявление недоступно для просмотра.» при проверке URL, ID и
snapshot; последние три — точные поддерживаемые формулировки, не заявление об
их наблюдении. Raw не меняется.
CAPTCHA, 429, блокировка сайта, отсутствие точного статуса или несовпадение ID
останавливают сбор. Для ранее не наблюдавшегося статуса сначала сохраните
локальное доказательство и исправьте общий classifier с тестом, без угадывания.


## UI Next с отличающимся href

Если подтверждено, что href Next ведёт к другой выдаче, используйте `freeze
--ui-next --tab-id <targetId>` на собственной вкладке. Первая страница заново
загружается по наблюдённому URL. Следующие страницы открываются кликом по
свежему наблюдаемому Next; href и фактический URL сохраняются отдельно. Runner
ожидает устойчивый результат и проверяет путь, заголовок, выбранную профессию,
номер URL и видимый aria-current. При повторе он сначала проверяет текущую
страницу и не кликает повторно, если переход уже выполнен. Несогласованное
состояние останавливает сбор. Не строить URL страницы вручную. `continuation` и исправление профессии
по прежней URL-цепочке для UI Next не поддерживаются: не применять их к такой
очереди; при необходимости остановиться для отдельного общего исправления.
При несовпадении Next сохраняется локальный `next-comparison.json` с URL, href
и scoped snapshot; без подтверждения причины повторять переход нельзя.

Если до plan/queue/raw сохранён частичный freeze с недостоверной принятой
страницей, по явной инструкции человека используйте `archive-uncertain-freeze
--run-id <id> --reason <причина>`: исходные байты и хеши сохраняются локально,
журнал ошибок и бюджет остаются неизменными. Затем используйте `freeze --resume`
с новым наблюдением и прежним бюджетом. Не использовать для готовой очереди.

## Проверка Git при публикации

Publish проверяет unmerged index и `git diff --cached --check`. Только для файлов
CSV/JSON внутри Data допускается диагностированная строка из семи знаков `=` с
последующим содержательным текстом как наблюдаемый текст; настоящие маркеры
конфликта и остальные замечания Git по-прежнему блокируют публикацию. После
finalize изменения кода, теста и skill регистрируют через note-change;
post-finalize-review проверяет неизменность экспорта и добавляет audit, не
переписывая manifest.

Удерживающий keeper пишет локальный `diagnostics/keeper-<pid>.local.log` с
началом, EOF или marker и ошибками. EOF сам по себе не определяет причину
завершения REPL; вкладка живёт только пока работает создавшая её сессия.
Для salary-review-policy достаточно прямой инструкции проверить исходный ID,
закрепить политику для последующих аналогичных случаев и продолжить очередь.

Если сохранённый raw содержит UNKNOWN_PAGE с source_url `about:blank`, а полный
snapshot подтверждает пустые title и URL, это непрочитанная карточка, не skip.
После отдельного разрешения с ID и `about:blank` выполните resume-browser и
preserve-stopped-observation: команда сверит очередь, checkpoint, raw и snapshot
с исходным sandbox, сохранит байты и provenance, освободит raw-слот для чтения
того же ID. Иные страницы и ограничения доступа этим маршрутом не обрабатывать.

REPL и keeper запускаются в отдельных процессных сессиях; это снижает
зависимость от группы запуска, но не гарантирует сохранность при внешнем
завершении. В keeper log фиксируются PID и состояние при передаче дескрипторов.


## Отключённая стрелка Next

Extractor распознаёт также немаркированную кнопку `aria-disabled=true` внутри
`pagination-button` и `listItem_arrow_next` с SVG `arrowright`. Отключённые
многоточие и Previous не подтверждают конец. Уже сохранённые страницы и план
не переписывают; отдельный review с доказательством фиксирует наблюдение.
Изменённый extractor требует нового наблюдения в новом run; закреплённый пакет
продолжает использовать исходный extractor.


## Более строгий внешний порог ошибок

Если инструкция человека остановила технический сбор после двух ошибок, а ledger
показывает RETRY_AVAILABLE и в нём остаются повторы, после прямого разрешения
человека зафиксируйте его через `external-threshold-authorization --run-id <id>
--human-instruction '<точная инструкция>' --authorization-id '<стабильный ID>'`.
Команда сохраняет историю и счётчики без пополнения бюджета; не применяется к
NEEDS_HUMAN, CAPTCHA и иным немедленным остановкам. Перед дальнейшим действием
нужна конкретная коррекция через `--retry-reason`. При существующем каталоге
без плана повтор freeze выполняйте с `--resume`; для UI Next также обязателен
`--tab-id`. Перед возобновлением подготовки без плана выполните fetch и используйте
свежий checkout, перенеся локальный журнал целиком без изменения.


## Один диагностический возврат после потери Aside

После подтверждённого восстановления соединения и прямого разрешения на один
возврат к конкретному pending ID используйте `diagnostic-pending-capture` с
`--run-id`, `--id` ожидаемой карточки, `--tab-id` новой собственной вкладки, `--human-instruction`,
`--authorization-id` и `--connection-evidence` с проверенным свидетельством.
Команда применима только к сохранённому CDP Page.navigate timeout или точной ошибке
`Error: Session with given id not found.` и отсутствующему
raw pending ID. Она сохраняет локальные указатели исходной ошибки с хешами,
не завершает прежнюю вкладку и выполняет не более одного чтения. При NEEDS_HUMAN общий ledger остаётся остановленным. При RETRY_AVAILABLE команда
расходует один оставшийся повтор, без сброса бюджета; успешное наблюдение позволяет
продолжить по прямому разрешению человека, новая ошибка немедленно останавливает. Нельзя использовать её для CAPTCHA, блокировки или смены
профиля/сети. Изменения runner и skill зарегистрируйте через note-change.
