# Нештатные случаи collect-avito

Читайте только при соответствующей проблеме.

## Остановка и продолжение

CAPTCHA, ограничение доступа, неожиданный ID или непонятная страница останавливают
новые переходы; сохраните состояние `NEEDS_HUMAN`/`REVIEW_REQUIRED` и причину.
Не извлекайте скрытое содержимое под блокировкой. Следуйте согласованной
политике ожидания; автоматического обхода блокировки в этом навыке нет.

При resume прочитайте существующий checkpoint и raw. Подтвердите ту же выборку
и текущую страницу по фактическому URL/ID. Вкладки и refs прошлого процесса
не переиспользуются вслепую. Не загружайте уже сохранённые ID повторно;
новое наблюдение того же ID храните отдельно с новым временем. Завершённый
каталог не продолжайте: новый сбор получает новый каталог.

## Выход и проверка

Основной результат для команды — **актуальный `Data/dataset/vacancies.csv`**,
общий для Analytics и ML. Сначала сохраните отдельный неизменяемый CSV сбора:
одна строка на уникальную принятую вакансию, параметры в отдельных колонках.
Его должно быть достаточно для `pd.read_csv(...)`, без чтения raw или паспорта
и без разбора JSON в ячейках. Сохраните ID, URL, время наблюдения, город,
профессии/сегменты отбора, исходную зарплатную строку, описание и ограничения.
Добавьте `listing_rank` (позиция в зафиксированной очереди) и `listing_promoted`
(`True`/`False` по наблюдённой отметке продвижения); неизвестное оставьте пустым.
При нескольких сегментах сохраните все значения через `; `, не дублируя вакансию.
Отсутствующие значения оставляйте пустыми, не подменяйте их нулём или «нет».
Обязательные колонки, допустимые статусы и служебные поля определены в
[контракте](../../../../Data/dataset/README.md). Для схемы первой выгрузки есть
офлайн-преобразование `utils/flatten_export.py`; новую схему проверьте отдельно.
Ссылку на CSV добавьте в `Data/README.md`. Архив raw — дополнительный материал,
он не должен быть обязательным для открытия готовой таблицы.

Обогащение из описания запускайте в согласованном объёме. При отсутствии
обогащения явно ставьте `enrichment_status=not_run`; при завершении —
`completed`, `enrichment_version` и `enriched_fields`. Для каждого заполненного
из описания поля сохраняйте `<поле>__source=description` и `<поле>__evidence`
с точной цитатой из сохранённого описания. `completed` с пустым списком означает,
что обработка выполнена, но новых значений не найдено. Ошибку отмечайте `failed`,
не публикуя частичные результаты как завершённые. Явные параметры не затирайте
выводами из описания; противоречия сохраняйте отдельно. Для исторических данных
без разметки происхождения допустим `unknown`.

`Data/avito_runs/<run_id>/`: raw JSON, проверенные карточки, компактные
сведения о фильтрах/очереди и `exports/` с CSV/JSON. План и описание набора храните отдельно в
`Scraper/runs/<run_id>/plan.json` и `manifest.json`; технические журналы и
checkpoint — локально в `Scraper/runs/<run_id>/diagnostics/`. В общий экспорт
их не включайте. DOM/HTML-дампы, accessibility snapshots и скриншоты
не публикуйте в GitHub; существующие исторические архивы не переписывайте.
Manifest перечисляет только опубликованные файлы, без путей к локальной
диагностике. Основной плоский CSV кладите в `exports/vacancies_flat.csv`,
не дублируйте его в корне Data. Макет описания —
[Scraper/templates/manifest.template.json](../../../templates/manifest.template.json).
Зафиксируйте версию инструкции (Git-коммит или hash), схему полей, модель
агента/настройки если известны, план и факт, уникальные ID, ошибки и stop_reason.

Одна карточка проверяется локально:

```sh
python3 Scraper/skills/collect-avito/scripts/check_capture.py --raw <файл.json> --expected-id <ID>
```

Это проверка структуры и идентичности, не полноты чтения, репрезентативности
или правдивости работодателя. Финально сверяйте очередь и файлы, число
включений и уникальных ID, фактическое покрытие плана, описания и ограничения.
Сохранённое и принятое после проверки — разные числа. Ссылки на полученные
данные добавьте в исследование и задачу; людей/статусы не назначайте догадками.


## Публикация и конфликт main

Сначала прочитайте [OUTPUT_CONTRACT.md](OUTPUT_CONTRACT.md): различия трёх
служебных файлов, Windows-хеши и маршрут публикации из fork. Если человек
отложил разрешение конфликта, сохраните текущий PR и остановитесь до merge.

Перед публикацией получите свежий **командный** main: `git fetch origin main`
в общем репозитории, `git fetch upstream main` при origin на личный fork.
Подготовьте ветку `codex/<run_id>` от соответствующего origin/main или upstream/main.
Если изменения уже находятся в своей ветке, включите свежий командный main
и пересоберите производные файлы. Не сбрасывайте
чужую работу и не переносите весь рабочий каталог. При загрязнённом checkout
используйте отдельный checkout и только явно перечисленные файлы своего сбора.
При праве записи работайте веткой общего репозитория; участник без права
записи использует личный GitHub fork, актуализированный относительно upstream.
Повторный fork перед каждым сбором не нужен; синхронизация main обязательна.

Добавьте только свои данные, реестр, общий CSV/manifest, паспорт и каталог.
Проверьте staged diff, выполните commit и push после завершения всех технических
пакетов согласованного сбора и финальной проверки, затем откройте PR. Push
сохраняет результат на GitHub ещё до слияния. Технический пакет capture не
получает отдельный run_id, CSV, вызов Terra или публикацию: продолжайте общую
очередь с checkpoint. Отдельные завершённые сборы с собственными run_id допустимы,
если именно такое разделение заранее задано участником; не дробите один сбор
на маленькие самостоятельные публикации по умолчанию. Непроверенные строки
остаются в локальном checkpoint и не публикуются как принятые данные.

Коммит данных: `data: <run_id> (<N> вакансий)`; заголовок PR:
`Данные: <N> вакансий · <условие> · <география>`.
Описание — один абзац об отборе, затем bullets с принятыми ID, новыми/повторными
наблюдениями, размерностью до/после и новыми характеристиками; в конце одна
строка о CSV, raw JSON, плане/паспорте и проверке. Без длинных интерпретаций,
пересказа переписки и истории настройки VPN; существенное ограничение кратко
поместите в первый абзац, детали — в паспорт.
Готовый текст формирует [dataset_pr.py](../../../../utils/dataset_pr.py). Пример
для командного origin (в fork замените --base на upstream/main):

```sh
python3 utils/dataset_pr.py --run-id <run_id> --base origin/main \
  --summary "Собраны первые 5 вакансий с графиком Вахта по всем регионам." \
  --output /tmp/dataset-pr.md
```

Запустите после `git add`, до commit: утилита проверяет --check и блокирует
публикацию staged снимков браузера. Посмотрите точный результат, затем используйте
`gh pr create --body-file /tmp/dataset-pr.md` в ветке общего репозитория. Для
fork используйте prepare-only и явные --repo/--head по OUTPUT_CONTRACT.md,
а не обычный publish. Прикрепите PR к чату, если доступно.
Перед merge проверьте актуальность относительно свежего командного main, локальные тесты,
`python3 utils/build_dataset.py --check`, отсутствие незавершённых обязательных
проверок/reviews. Зафиксируйте проверенный head SHA и выполните обычное слияние
с проверкой этого SHA (например, `gh pr merge --merge --match-head-commit <SHA>`).
Не используйте force-push и admin bypass. Если GitHub требует review или
не даёт merge, оставьте сохранённую ветку/PR и сообщите конкретное требование.
После merge получите командный main (origin/main или upstream/main) и в чистом
временном checkout проверьте CSV,
число уникальных ключей и --check. Только после этого сообщайте «данные в main».
При недоступном GitHub сохраните локальные файлы и сообщите причину.

При параллельном изменении реестра обновите ветку, сохраните записи обоих
сборов и пересоберите CSV/manifest; их Git-конфликты разрешаются пересборкой.
Финально покажите размер общей таблицы, небольшой пример строк и результат
`--check`. Если установлен `.github/workflows/dataset.yml`, GitHub Actions
проверяет соответствие таблицы реестру и тесты. До его установки проверки
выполняются локально; готовый шаблон находится в `Scraper/templates/`.


## Продолжение после разрешения человека

Технические ошибки допускают пять осмысленных повторов по общему SKILL.md;
повторный check-stage одного активного этапа не является ещё одной попыткой.
После NEEDS_HUMAN новое явное разрешение на чтение сайта регистрируют командой
resume-browser с новым authorization-id этой инструкции человека. История
сохраняется. Для старого разрешения ID не меняют, чтобы повтор команды не
обновлял бюджет. Разрешение на обработку сохранённого — только resume-offline.


## Git push: недоступен системный credential helper

Если publish записал ошибку git push, сначала проверьте её локальную диагностику:
код 128 сам по себе не доказывает проблему авторизации. Для HTTPS GitHub,
когда причина именно в недоступном системном helper, а `gh auth status`
подтверждает действующую авторизацию, можно выполнить осмысленный повтор ниже.
Не запрашивайте токен/повторный login и не меняйте глобальные Git-настройки.

```sh
GIT_CONFIG_COUNT=2 \
GIT_CONFIG_KEY_0=credential.helper GIT_CONFIG_VALUE_0= \
GIT_CONFIG_KEY_1=credential.helper GIT_CONFIG_VALUE_1='!gh auth git-credential' \
python3 Scraper/skills/collect-avito/scripts/run.py publish --run-id <id> \
  --summary '<условия того же сбора>' --title '<заголовок того же PR>' \
  --retry-reason 'Подтверждён сбой системного credential helper; используем уже авторизованный gh только для этой команды'
```

Переменные действуют только для этого вызова. Если GIT_CONFIG_* уже используются
окружением, сохраните их пары и добавьте override, не затирая другие параметры.
Обычный лимит повторов/NEEDS_HUMAN остаётся в силе. Команда переиспользует уже
созданный commit/PR и не собирает карточки заново. Путь проверен при публикации
first5_2026-10-28_01 в TL Demo test; его история сбоев осталась локальной.
