# Единый результат сбора: Codex и Claude Code

Прочитать проверяющему перед finalize/publish; ведущему — при первом запуске,
работе из fork или расхождении форматов. Каноническая схема и политика обновления:
[Data/dataset/README.md](../../../../Data/dataset/README.md). Приложение и модели
меняют способ делегирования, общий runner и контракт файлов остаются одними.

## Что сдаёт сбор

| Файл | Назначение и способ получения |
|---|---|
| `Data/avito_runs/<run_id>/exports/vacancies_flat.csv` | Основной самодостаточный CSV, одна строка на принятый ID, полные описания и характеристики; создаёт finalize |
| `Data/avito_runs/<run_id>/` | Очередь, listing/listing_pages, raw, reviewed и exports; состав определяет runner |
| `Scraper/runs/<run_id>/plan.json` | Фильтры, режим отбора, время, версия/commit и хеши реально использованного кода; фиксирует freeze |
| `Scraper/runs/<run_id>/manifest.json` | Паспорт конкретного сбора: покрытие, схема, тайминги, модель проверки, хеши файлов и зарегистрированные изменения; создаёт finalize |
| `Data/dataset/sources.json` | Реестр неизменяемых исходных CSV, по одной записи на run_id; finalize добавляет свой источник, прежние записи сохраняются |
| `Data/dataset/vacancies.csv`, `Data/dataset/manifest.json` | Общая таблица и её паспорт; целиком генерирует `utils/build_dataset.py` по реестру |
| `Data/README.md`, `Data/dataset/README.md` | Ссылка на новый набор и актуальная размерность; обновляет finalize |

Готовый CSV открывается через `pd.read_csv(..., dtype={"id": "string"})` без
дополнительного преобразования. Не создавайте альтернативный экспортёр или
Claude-колонки, не пересобирайте характеристики вручную. Формат значений задаёт
текущий runner: старые наборы могут использовать другой разделитель списков.
Число колонок не фиксировано; новые наблюдённые характеристики допустимы.
Домыслы из описания не выдаются за параметры карточки. Неизвестное остаётся пустым.
DOM, screenshots, checkpoint, failures.json и локальные конфиги в PR не входят.

## Почему меняется общий manifest

`Data/dataset/manifest.json` содержит колонки, размерность, хеш общего CSV,
хеши сборщика и `inputs` всех зарегистрированных выгрузок. В `inputs` копируются
записи sources.json, включая placement_regions и unknown_city_placements,
с добавленным числом строк. Это не повторная регистрация источников и не
история диалога. Большой diff сам по себе не означает лишние данные.

Нормальный новый сбор добавляет одну запись источника и один соответствующий
input; меняет общий хеш/размерность, при необходимости колонки. Старые записи
не редактируются ради сокращения diff. Не удаляйте inputs/географические
исключения и не исправляйте SHA вручную. После finalize выполните:

```sh
python3 utils/build_dataset.py --check
```

Код 0 подтверждает соответствие производных файлов текущему реестру и коду.
Он не доказывает, что город распознан правильно, человек прочитал карточки,
исправления кода вошли в PR или ветка содержит свежий командный main.
При видимом городе, который парсер оставил пустым, проверьте общий маршрут
placements из SKILL.md. Не заполняйте географию по описанию или URL.

## Повторные вакансии: проверять целиком

Повторный ключ `(source, id)` допустим: это новое наблюдение, а не новая
вакансия. В общем CSV выбирается **целиком** строка с самым поздним observed_at;
старый исходный CSV сохраняется, first_seen_at остаётся первым, run_ids
накапливает сборы. Пустые поля новой версии не дополняются старой строкой.
Поэтому пропавшая колонка тоже может стереть прежнее значение в общей таблице.

Перед публикацией сравните новый пакет со свежим командным main по `(source, id)`:
новые/повторные ключи и все изменившиеся значения общей строки, включая поля,
отсутствующие в новом CSV. Отдельно перечислите время/просмотры, rank/promoted,
дату публикации, параметры/зарплату/географию/описание и исчезнувшие значения.
Если новых полей нет, это не означает, что старые значения не изменились.
Различайте текстовые изменения и изменение условий: похожие латинские/кириллические
буквы, пробелы и разделители списков могут менять строку без изменения смысла.
Сохраняйте исходный текст; нормализация для сравнения не изменяет raw или CSV.
Не утверждайте «только просмотры», пока не проверены остальные колонки.
Существенное изменение условий или потерю значений кратко укажите в summary PR.

## Код, хеши и Windows

До freeze нужен отдельный checkout от свежего командного main. До начала
наблюдений проверьте runner/extractor/instruction относительно выбранного commit:
либо байты совпадают, либо есть реальный документированный diff общего исправления
с тестом и skill. План сохраняет фактические хеши и uncommitted_automation_files;
одного HEAD для подтверждения чистоты недостаточно. На Windows core.autocrlf может оставить в рабочей копии
CRLF при LF в Git: пустой git diff не доказывает совпадение байтов и SHA-256.
Хеши проекта считаются по байтам, а не по нормализованному тексту.

Если обнаружено только преобразование окончаний строк, **до freeze** создайте
новый checkout с LF для кода, не меняя глобальные настройки Git, например:

```sh
git -c core.autocrlf=false -c core.eol=lf worktree add -b codex/<новая-ветка> <новый-путь> <командный-remote>/main
```

Сначала fetch выбранного remote; пути/ветка должны быть новыми. После создания
проверьте фактические байты кода и build_dataset --check. Атрибуты `-text` у
архивов Data/avito_runs сохраняются: исходные данные не конвертировать.
Если план/raw уже есть, не перекодируйте их и не переписывайте записанные хеши:
сохраните происхождение и разберите исключение офлайн по общему skill.

`automation_changes` — список реальных исправлений, не список всех файлов с
другими окончаниями строк. Для каждого исправления нужны общий код, регрессионный
тест и обновление skill в diff этого PR; каждый затронутый файл регистрируют
через note-change с причиной и проверкой по основному skill. Исправление, уже
принятое до freeze, относится к закреплённому commit и не добавляется как новое
automation_change этого run. Ссылка на другой PR не заменяет требования runner
к зарегистрированным файлам, тесту и skill. Не откатывайте исправление перед
commit, оставляя его в паспорте.
Фактические результаты вроде «45/47» содержат две ошибки: выясните их причины;
не представляйте такой запуск как полностью пройденный. Отличайте платформу,
на которой выполнена проверка, от платформ, для которых есть только ветка кода.

После commit, **до признания PR готовым и merge**, сверьте каждый
`files[path].bytes/sha256` паспорта с байтами `git show HEAD:<path>`, включая
plan.json из Scraper/runs. Обычный publish выполняет commit/push/PR подряд:
в этом маршруте сверку выполняют сразу после publish, до merge. При prepare-only
проверьте байты после ручного commit и до push. Проверка
рабочего дерева через publish этого не заменяет: Git может нормализовать текст
при добавлении в index. Если любой файл не совпадает с паспортом,
остановитесь с описанием расхождения; общий build_dataset --check такой дефект
не обнаруживает. Не исправляйте паспорт задним числом ради зелёной проверки.

## Публикация из общего репозитория или fork

Перед публикацией ведущий фиксирует: командный remote/ref, его свежий SHA,
репозиторий для push и целевой `tooscl/salary-navigator:main`. Общий remote —
origin при работе в командном репозитории, upstream при origin на личный fork.
Делегированному проверяющему передаются эти значения вместе с run_id.

Обычная ветка общего репозитория использует `run.py publish`. В текущем runner
publish проверяет `origin/main`, а dataset_pr.py по умолчанию сравнивает с ним же.
В fork этого недостаточно: свежесть origin/main не доказывает свежесть upstream.
Получите командный main, проверьте его включение в HEAD через
`git merge-base --is-ancestor <командный-remote>/main HEAD`. Если main ушёл вперёд,
поступайте по edge-cases; при запрете разбирать конфликт сохраните PR без merge.
Даже при одинаковом формате параллельные сборы могут конфликтовать в общей таблице.

Для fork подготовьте stage и проверки через `run.py publish --prepare-only`
с обычными --run-id/--summary/--title. Эта команда тоже требует включённого
origin/main; при расхождении не обходите проверку. Затем перегенерируйте текст
по **командному** main, просмотрите staged diff и сам файл описания:

```sh
python3 utils/dataset_pr.py --run-id <run_id> --base upstream/main --summary '<отбор и ограничения>' --output <локальный-путь-pr.md>
```

Используйте фактическое имя командного remote вместо upstream при необходимости.
После проверок commit имеет вид `data: <run_id> (<N> вакансий)`; push — в свою
ветку fork. Создайте PR с явными репозиторием, head и файлом описания:

```sh
gh pr create --repo tooscl/salary-navigator --base main --head <владелец-fork>:<ветка> --title 'Данные: <N> вакансий · <условие> · <география>' --body-file <локальный-путь-pr.md>
```

Не передавайте многострочный текст через shell-подстановки. После создания
прочитайте опубликованный body: он должен содержать отбор, новые/повторные ID,
размерность, новые характеристики и проверки из dataset_pr.py. Пустой body —
незавершённая публикация. Проверьте также base/head и приложите ссылку к чату.
Merge — только в рамках задания и обычных reviews/защиты ветки.

Финальный ответ участнику: принятые/новые/повторные ID, размер общей таблицы,
ссылка на CSV и PR, существенные изменения повторов/пропуски, проверки,
фактические модели/alias и версия/commit. Статусы «CSV готов», «PR открыт» и
«в main» должны соответствовать выполненным действиям.
